# Sound driver manual — Mad Mix Game (ZX Spectrum 48K, `$FE` beeper)

*[Leer esto en español](manual_driver_sonido.md)*

*Reverse engineering, analysis and documentation: Rafael Eduardo Martín Candial (raemca@hotmail.com)*

> Source: `src/madmix_body.asm`, region `$DBE0`-`$EFB5` (music engine,
> subpatterns, effect table, demo scripts) plus `DESPACHAR_EFECTO_SONIDO`
> (`$8F55`) and `REPRODUCIR_SONIDO` (`$E1F9`). For the chronicle of how
> each piece was discovered, see `FINDINGS.md`; this document assumes
> everything is already identified and explains the final result in an
> orderly way.

## 1. What this is and what it is NOT

This manual explains how the game generates sound on a real ZX
Spectrum 48K from tape: **there is no dedicated sound chip at all** —
everything goes through a single bit of port `$FE`, the very same port
shared with keyboard and tape. From that single binary signal, the
game builds 2 "channels" of music by software multiplexing, an
independent short-effects system, and its own 6-command bytecode
language for the songs.

**Fundamental difference from the sister MSX project**: the MSX1 has a
dedicated sound chip, the PSG AY-3-8910 (3 hardware tone channels +
noise, see MSX's `manual_driver_sonido.md`). The ZX Spectrum 48K **has
no sound chip whatsoever** — confirmed by the total absence of any AY
port access (`$FFFD`/`$BFFD`) anywhere in `madmix_body.asm`, and by the
exclusive presence of `OUT ($FE),A` (21 occurrences) as the only audio
mechanism. This is the **48K tape** version — there is no sign of
memory paging or 128K support anywhere in the code. All the "sound"
actually heard while playing is a single square wave (or a
superposition of several, switched very fast) over that one beeper
bit.

**It is not** a single player: it is really **three independent
subsystems** with distinct architectures (§2), and they should not be
confused with each other, nor with a fourth data format that shares
their "look" but is not sound at all (§2.3).

## 2. The three (plus one) audio subsystems

### 2.1 The music engine — blocking, 2 multiplexed channels

Plays the game's 3 songs/jingles (title screen, level start, special
mode ending). **It hogs the CPU completely while it plays** — it is a
foreground busy-loop (`BUCLE_TONO_CANAL_A`, inside `REPRODUCIR_SONIDO`,
`$E1F9`) that does not return control until the song finishes or the
player presses a key. In the meantime, **neither the game nor screen
redrawing advances** — the engine's normal interrupt handler
(`ENTRADA_INTERRUPCION_VBLANK`, which calls `TICK_REDIBUJADO_VBLANK`
and `DESPACHAR_EFECTO_SONIDO`) is **replaced** by the music player's
own service routine (`ISR_SONIDO`) for the duration of the song — so
sound effects and redrawing are suspended too, not just the main loop.

Two "channels" simulated by software over the same beeper bit:

- **Channel A** (`IX` register): tone/melody. The actual tone (the
  square wave) is generated by the foreground busy-loop itself, not
  the interrupt — with two self-modifying counters (full period and
  half period) that toggle the beeper bit.
- **Channel B** (`IY` register): percussion. Its events are short and
  generated **directly inside the interrupt** (`ISR_SONIDO`), without
  going through the foreground loop.

Since there is only one physical beeper bit, both channels overlap on
the same signal: channel A dominates CPU time (foreground busy-loop)
and channel B briefly cuts in whenever the interrupt triggers it —
software multiplexing with interrupt-driven timing, the classic
pattern for Spectrum 48K beeper players.

### 2.2 Short sound effects — non-blocking

Plays the 12 gameplay effects (eating a pellet, activating a special
item, etc. — full table in §4). Unlike the music engine, **it does not
block the game**: `DESPACHAR_EFECTO_SONIDO` (`$8F55`) is called once
per interrupt (50 Hz) from the game's own normal ISR, advancing one
step (a duration/period pair) per interrupt — the whole game keeps
running, the effect is spread across several frames. It only has **1
"channel"**, with no script commands or subpatterns — the simplest of
the three systems.

### 2.3 Demo scripts — NOT sound

An important warning to avoid confusing formats: there is a third data
type that "looks like a sound script" (pairs of small bytes ending in a
special value) which **has nothing to do with audio** — these are
prerecorded input scripts for the demo/attract mode (`INICIAR_DEMO`),
format pairs `(frame_threshold, direction)` ending in `$FF,$FF`, which
feed `MOTOR_MOVIMIENTO_COLISION`, not the speaker. They are mentioned
here only because an intermediate hypothesis during the investigation
(see §11) initially confused them with music data — the permissiveness
of the music engine's bytecode format (almost any byte has *some*
valid reading as a note or command) means "decodes without errors" is
not, by itself, proof that something is really a music script.

## 3. The music engine's bytecode language: 6 commands

Format of the 3 songs and their 43 shared subpatterns
(`$DD18`-`$E023`), one command byte per step:

| Byte / range | Mnemonic | Meaning |
|---|---|---|
| `$00`-`$F9` | `NOTE 0xNN` | **Channel A**: bits 0-5 = index into `TABLA_TONOS_CANAL_A` (pitch); bits 6-7 = index into `TABLA_DURACIONES` (duration). **Channel B**: bits 0-2 = index 0-7 into `TABLA_PERCUSION` |
| `$FF` | `END` | End of script. On channel A sets `FLAG_ESTADO_SONIDO=2` ("finished"), triggering `DETENER_SONIDO`; on channel B it just returns from the interrupt without stopping the engine |
| `$FE` | `RESET` | Resets duration to the default value (`TABLA_DURACIONES`, index 0) without touching the active pitch |
| `$FD nn nn` | `CALL 0xNNNN` | Calls a subpattern by absolute 16-bit address, pushing the return address onto a **per-channel private stack** |
| `$FC` | `RETURN` | Returns from the current subpattern (pop from the private stack) |
| `$FB` | `PATCH1` | Self-modifying code: overwrites 8 executable bytes of `TONO_PATRON_BASE` (`$E24D`-`$E254`) with the `PATRON_TONO_1` variant (channel A only) |
| `$FA` | `PATCH2` | Same as `PATCH1` but with `PATRON_TONO_2` (restores the original ordering, channel A only) |

Design notes: calls use absolute 16-bit addresses, not table indices —
a simpler format than MSX's (which needs an external address map); the
end marker lives inside the script itself (`$FF`), not in a separate
table. `$FB`/`$FA` are genuine cases of commands that rewrite
executable instructions instead of loading a simple parameter — their
mechanical effect (which bytes get overwritten) is identified, though
their exact audible musical effect has not been characterised by ear.

Each channel has its own private stack (`PILA_CANAL_A`/`PILA_CANAL_B`,
pointing into 50/18 bytes of real space in `PILA_CANAL_A_MEM`/
`PILA_CANAL_B_MEM`) so that `CALL`/`RETURN` work independently between
channels.

## 4. Short sound effects: no commands, just data pairs

Format: `(duration, period)` pairs in decimal, terminated by `$FF` —
the same "note" format used by `TABLA_TONOS_CANAL_A`/
`TABLA_DURACIONES` in the music engine, but **with no script commands
at all** (none of `$FE`/`$FD`/`$FC`/`$FB`/`$FA`). Real example
(`EFECTO_SONIDO_02`, one of the 12 data blocks in `$8FF5`-`$9049`, 117
bytes total): `DB 4,130, 8,6, 10,10, $FF`.

## 5. Triggering effects from the game: `EVENTO_SONIDO_PENDIENTE`

Same variable name, same underlying mechanism as its MSX counterpart:
`EVENTO_SONIDO_PENDIENTE` (`$8FD6`, 1 byte, `$FF` = "no event
pending").

- **Writer**: 24 different spots in the engine (mostly
  `TABLA_MANEJADORES_LOSETA` and `ACTIVAR_EFECTO_ITEM`) flag a pending
  effect with `LD A,<index>` / `LD (EVENTO_SONIDO_PENDIENTE),A`.
- **Consumer**: `DESPACHAR_EFECTO_SONIDO`, called once per interrupt
  from `ENTRADA_INTERRUPCION_VBLANK`. If the index is `$FF` there is no
  new event, but whatever effect was already playing still advances one
  step.
- Valid index: 0-11, resolved via `TABLA_RECURSOS_SONIDO_EVENTO`
  (`$8FDD`, 12 pointers to the effect scripts).

### Game event → effect map

| Index | Game event that triggers it |
|---|---|
| 0 | Eating a regular pellet/point |
| 1 | Eating a special/power pellet |
| 2 | The "auto-hero" changes direction |
| 3 | Activating/collecting a special tile item (power ball, hippo, drill-phone, tank/plane track, floor item) |
| 4 | A new tank/plane track gets registered |
| 5 | "Maricoco" respawn |
| 6 | "Repugnantoso" respawn |
| 7 | Tank/plane track proximity warning; points scored during a special mode |
| 8 | A special mode starts (power ball / hippo) |
| 9 | A trapdoor opens |
| 10, 11 | No known trigger in the code (never written); both also share a silent script (`$FF` with no pairs), so they would play mute even if triggered |

There is also a datum with the same effect format
(`EFECTO_SONIDO_HUERFANO`, `$9003`) that no table entry references —
candidate for a retired effect, unconfirmed.

## 6. Architecture of `REPRODUCIR_SONIDO` (`$E1F9`)

The music engine's real external entry point, called from 4 places
(`ESPERAR_TECLA_INICIO`, the new-game wait loop, `BUSCAR_COLUMNA_HUD`
and `BUCLE_PRINCIPAL_JUEGO`):

1. Clears both channels' state/duration flags.
2. `DI`; saves the game's normal IM2 vector (`$6061`) into
   `ISR_VECTOR_GUARDADO`, and installs `ISR_SONIDO` as the new vector —
   the 50 Hz clock now feeds the music player instead of the game
   engine.
3. Loads the channel pointers (`IX`/`IY`), already written by the
   caller, into the self-modifying `LD IX,nn`/`LD IY,nn` operands
   (`$E212`/`$E216`) — which song plays is decided by the caller before
   the `CALL`, not by `REPRODUCIR_SONIDO` itself.
4. Initialises each channel's private stack.
5. `EI`; enters `BUCLE_TONO_CANAL_A`, the blocking busy-loop: reads the
   keyboard every pass (to allow aborting with any key except the
   fixed-map ones), checks whether channel A has finished
   (`FLAG_ESTADO_SONIDO=2`), and if there is an active note generates
   the real tone by toggling the beeper bit with two self-modifying
   counters (full period and half period).
6. Every interrupt, now serviced by `ISR_SONIDO`, decrements each
   channel's duration counters; on reaching 0, it reads and dispatches
   the next script byte (the 6 commands from §3).
7. `DETENER_SONIDO`: `DI`, restores the original IM2 vector, `RET`.

**Self-modifying code, 4 distinct spots** (one of them, the active
tone period inside the tone loop itself, was overlooked in an initial
manual analysis and only confirmed by simulating the real code — see
§11): each channel's duration counters, each channel's script
pointers, the `$FB`/`$FA` patches over `TONO_PATRON_BASE`, and the
active tone period inside `BUCLE_TONO_CANAL_A`.

## 7. Architecture of `DESPACHAR_EFECTO_SONIDO` (`$8F55`)

1. `DI`; reads `EVENTO_SONIDO_PENDIENTE`.
2. If it is `$FF`, jumps straight to advancing the effect in progress.
3. If there is a new index, resolves it in
   `TABLA_RECURSOS_SONIDO_EVENTO`, installs the pointer as the active
   script, and clears `EVENTO_SONIDO_PENDIENTE` to `$FF` (consumed).
4. Reads the next `(duration, period)` pair from the active script.
   `$FF` = end (does nothing more this tick); duration 0 = silence this
   step but the pointer still advances.
5. With duration > 0, generates the tone with the same self-modifying
   dual-counter trick as the music engine, but with a **third duration
   counter** instead of delegating it to an interrupt flag — there are
   no channels to multiplex here. Same beeper bit as the music engine.

Since it runs inside the game's own normal interrupt, one effect
step's tone is generated in one go, in full, within that single
interrupt — not spread across several.

## 8. Data tables

| Table/variable | Address | Size | Content |
|---|---|---|---|
| `TABLA_TONOS_CANAL_A` | `$E2B8` | 64 words | Tone periods, descending chromatic scale; only 41 entries in real use, verified by simulation against real musical frequencies |
| `TABLA_DURACIONES` | `$E2AE` | 4 bytes | `5, 11, 17, 23` frames, indexed by bits 6-7 of the note |
| `TABLA_PERCUSION` | `$E29A` | 8 pointers | Only 4 real noise routines, each duplicated to fill the 8 indexable entries |
| `FLAG_ESTADO_SONIDO` | `$E2AA` | 1 byte | 0=silence, 1=playing, 2=finished |
| `ISR_VECTOR_GUARDADO` | `$E2AB` | 2 bytes | The game's original IM2 vector, saved/restored by `REPRODUCIR_SONIDO`/`DETENER_SONIDO` |
| `PILA_CANAL_A`/`PILA_CANAL_B` | `$E2B4`/`$E2B6` | 2+2 bytes | Each channel's private stack pointer |
| `TABLA_RECURSOS_SONIDO_EVENTO` | `$8FDD` | 12 pointers | Addresses of the 12 short-effect scripts |
| `EVENTO_SONIDO_PENDIENTE` | `$8FD6` | 1 byte | Trigger mechanism from the game engine (§5) |

The 3 real songs, with their channel A/B scripts:

| Song | Size | Trigger | Moment |
|---|---|---|---|
| `CANCION_PRESENTACION` | 80 bytes | `ESPERAR_TECLA_INICIO` / new-game wait | Title screen / starting a new game |
| `CANCION_INICIO_NIVEL` | 14 bytes | `BUSCAR_COLUMNA_HUD` | Every time a level starts being played |
| `CANCION_FIN_MODO_ESPECIAL` | 14 bytes | `BUCLE_PRINCIPAL_JUEGO`, when the special mode ends | End of power ball/hippo |

## 9. Tools: `mmsnd_tool.py` and `mmsnd_render.py`

```
py tools/mmsnd_tool.py disasm file.snd file.txt     # binary -> editable text
py tools/mmsnd_tool.py asm file.txt file.snd        # text -> binary
py tools/mmsnd_tool.py roundtrip file.snd           # verifies disasm+asm = same binary
py tools/mmsnd_tool.py roundtrip-all folder/         # same, for a whole folder
```

Text format: one instruction per line, with the §3 mnemonics
(`NOTE 0xNN`, `END`, `RESET`, `CALL 0xNNNN`, `RETURN`, `PATCH1`,
`PATCH2`) — a direct mapping of the bytecode's 6 commands.

```
py tools/mmsnd_render.py render file.snd output.wav [--channel A|B]
py tools/mmsnd_render.py render-pair channelA.snd channelB.snd output.wav
py tools/mmsnd_render.py render-all folder/ output_folder/
```

Options: `--rate` (44100 Hz by default), `--tickhz` (50 Hz),
`--max-ticks` (200), `--clock` (3.5 MHz). Unlike the equivalent MSX
tool (which reimplements the player's logic by hand in Python), this
one **actually runs the original Z80 code**: a minimal simulator runs
over a real copy of the binary, with simulated 50 Hz interrupts,
logging every `OUT ($FE),A` to reconstruct the square wave — chosen on
purpose because the manual analysis of the tone loop led to an
incorrect conclusion the first time around (§11); running the real
code avoids that kind of mistake.

> ⚠️ **Real editing limit** (same pattern as levels, see
> `manual_niveles.md` §8): every `.snd`/`.spt` file is compiled with a
> fixed-size `INCBIN`. You can freely change the VALUE of a note or the
> target of a `CALL`. **Do NOT add or remove lines**: the size is
> FIXED — the engine reads these bytes directly from RAM at the
> original addresses (`IX`/`IY` point at absolute, not relative,
> addresses); if the size changes, everything that follows in the
> rebuilt binary shifts address. Additional note: an "empty" channel A
> script cannot simply be a single `END` (`$FF`) if you only want to
> silence that channel without stopping the whole engine — `$FF` on
> channel A always triggers `DETENER_SONIDO`; use a run of `RESET`
> (`$FE`) instead.

## 10. Confidence and open items

The complete sound-engine data block (`$DBE0`-`$EFB5`) is fully closed
— not a single byte remains unidentified. What remains genuinely open:

- `PERCUSION_3`/`PERCUSION_4` read a table of 2 values per iteration
  from `$0280` (a low-RAM system zone, reused as scratch space) instead
  of computing percussion by formula like `PERCUSION_1`/`PERCUSION_2`
  do — what fills that address, and why that particular zone was
  chosen, is unconfirmed.
- 6 demo scripts (`GUION_DEMO_SINREF_1`-`6`, including 2 that were at
  one point mistaken for sound data, see §11) have a valid format but
  no index in the demo-profile table references them — candidates for
  discarded takes or an older version of the demo cycle.
- `EFECTO_SONIDO_HUERFANO` (`$9003`, §5): same format as the 12 active
  effects, with no table entry referencing it.
- Indices 10/11 of `TABLA_RECURSOS_SONIDO_EVENTO` are never triggered
  anywhere in the transcribed code, and would play mute even if they
  were.
- The exact musical/audible effect of the `PATCH1`/`PATCH2` commands
  (what difference is actually heard, beyond which bytes get
  overwritten) has not been characterised by ear.

## 11. Methodological note: a lesson about "decodes without errors"

Worth documenting a real stumble in the investigation, because it is
instructive beyond this particular project: at one point, a 189-block
stretch (`$E3D8`-`$EF9E`) was characterised as "189 orphan music
scripts", based on the bytecode disassembler walking through it with
no errors at all. This turned out to be **false** — that stretch is
actually the compressed bitmap of the loading-screen decorative frame
(see `manual_subsistema_grafico.md` §8) plus its attribute table,
with nothing to do with sound. The reason: the music engine's bytecode
format is so permissive (almost any byte from 0-255 has *some* valid
reading as a note or command) that walking through it without errors
is a much weaker proof than it looks at first glance. The lesson
applied ever since: confirming that a data stretch is really a sound
script requires more than the disassembler "swallowing it" cleanly —
it takes running or simulating the real code and cross-checking
sizes/addresses against something known for certain (in this case, the
exact size of a Spectrum screen).
